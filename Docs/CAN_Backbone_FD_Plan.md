# План: одна магистраль CAN FD + локальные classic-шины

Дата: 2026-10-17.  
Статус: **черновик решения** — после правок плат будет уточнён конечный результат.

Связанные темы: топология шкафа (Phoenix BUS = RJ45 = один CAN), локомотив как буфер/сборка, нейтральные каналы AI/AO, дисплеи за хабом.

---

## 0. Зафиксированное решение (рамка)

1. **Магистраль шкафа** (контакты Phoenix BUS и разъёмы RJ45 — **одна и та же** электрическая сеть CAN): **CAN FD, 125 кбит/с**, кадры до **64 байт**.
2. **Рейка локомотив ↔ аналоговые модули (AI/AO)**: **classic CAN, 50 кбит/с**, кадр **8 байт** на модуль.
3. **Хаб ↔ дисплеи**: **classic CAN, 50 кбит/с**.
4. Аналоговый модуль: не более **двух** каналов; комбинации AI/AI, AO/AO, AI/AO. Смысл данных (климат, вода, VFD, заслонка и т.д.) задаётся **только в схеме приложения**, не зашивается в CAN.
5. Локомотив: **буфер + сборка** на магистраль; не зеркальная пересылка каждого кадра модуля на ПЛК.
6. Трансивер **CA-IS3062VW** на магистрали при 125 кбит FD и длинных кадрах — **подходит** (даташит: до 1 Мбит/с, ISO 11898-2). Дорожки CANH/CANL не менять. Для data-phase выше 1 Мбит нужна другая микросхема.
7. Запас по скорости есть: при росте можно поднять data-phase FD до ≤1 Мбит без смены разводки платы.
8. Три порта FDCAN на ПЛК в текущей прошивке — деталь железа/кода; целевая архитектура шкафа — **одна расширяемая магистраль** для головных модулей (ПЛК, локомотивы, хабы, реле), а не три независимые магистрали, которые нельзя соединять через RJ45.

### Зачем BUS и RJ45 — один CAN

Малый проект: всё на одной DIN-рейке.  
Большой: модули на разных рейках, связь кабелями RJ45.  
Если CAN на шине и CAN на RJ45 разные — при расширении получится замыкание сетей или петля. Поэтому RJ45 — вывод **того же** backbone, не второй контроллерный CAN.

Локальные CAN (AI за локомотивом, дисплеи за хабом) с магистралью **не соединять**.

## 1. Протокол

### 1.1. Два мира шин

| Шина | Режим | Скорость | DLC |
|------|--------|----------|-----|
| Магистраль (BUS + RJ45) | CAN FD | 125 кбит/с | до 64 |
| Локомотив ↔ AI/AO | Classic | 50 кбит/с | 8 |
| Хаб ↔ дисплеи | Classic | 50 кбит/с | 8 |

### 1.2. Кадр аналогового модуля на рейке (classic, 8 байт)

Идентификатор (текущий ориентир): `0x301`.  
Смысл каналов **нейтральный** (не «влажность/температура» в протоколе).

| Байт | Содержание |
|------|------------|
| 0–1 | канал 1, int16 LE, 0.01 единицы |
| 2–3 | канал 2, int16 LE, 0.01 единицы |
| 4 | статус (неисправности каналов / АЦП и т.п.) |
| 5 | счётчик кадра |
| 6 | место модуля на рейке |
| 7 | номер рейки |

Имена вроде `humidity_pct` / `temperature_c` в коде — исторические ярлыки «канал 1 / 2».

### 1.3. Сборный кадр локомотив → ПЛК (FD, до 64 байт)

- Заголовок: рейка, число слотов, счётчик/поколение пачки.
- Слот (~6 байт): место, статус ch1/ch2, значение1, значение2.
- До **~8–10 модулей** в одном FD-кадре → на 30 модулей **3–4 кадра** подряд.
- Отдельный ID (или ID + индекс части пачки), не путать с одиночным `0x301`.

### 1.4. Сборный кадр заданий ПЛК → локомотив (FD)

- Рейка + слоты: место, канал, значение, флаги (AO).
- Локомотив разворачивает в classic-кадры на нужные модули рейки.

### 1.5. Прочее на магистрали

- Комната / привязка дисплея / двери / нумерация / прошивки: по магистрали в FD (допустимо DLC 8 внутри FD).
- На шину дисплеев — classic, как сейчас.

### 1.6. Конфиг канала (приложение → ПЛК)

Для каждого канала модуля: тип сигнала, направление AI/AO, величина (температура, влажность, давление, расход, позиция, задание VFD, другое…), min/max, привязка к оборудованию/комнате/контуру.  
ПЛК сопоставляет `(line/rail/place, channel)` с конфигом и решает, что делать с числом.

## 2. Настройки CubeMX

### 2.1. Магистраль (ПЛК — порт магистрали; локомотив — сторона ПЛК; хаб — сторона ПЛК; реле)

1. Frame Format: **FD** (сначала проще **FD without BRS** — всё на 125 кбит).
2. Nominal bitrate: **125 kbit/s**.
3. При BRS позже: Data bitrate 125…1000 (потолок CA-IS3062 = 1 Мбит).
4. Rx/Tx element size: **64 bytes**.
5. Пересчитать Message RAM / число элементов FIFO.
6. Auto retransmission: **Enable**.
7. Generate; прикладной код — в USER CODE / по инструкции MX пользователю.

### 2.2. Рейка AI и шина дисплеев

1. Frame Format: **Classic**.
2. Bitrate: **50 kbit/s**.
3. Element size: **8 bytes**.
4. Модули AI/AO и дисплеи на FD **не** переводить.

### 2.3. Локомотив / хаб

Два разных Init на двух FDCAN: один FD 125×64, второй classic 50×8.

---

## 3. Прошивка аналогового модуля

1. Остаётся classic 50, кадр 8 байт.
2. В коде: нейтральные «канал 1 / канал 2».
3. По конфигу: AI — измерение и периодическая отправка; AO — приём задания и выставка выхода; при необходимости обратная связь.
4. Период измерений по умолчанию: **1 с**.
5. Модуль не знает «комната» / «частотник» — только сигнал и диапазон.

---

## 4. Прошивка локомотива

1. CAN к ПЛК: FD 125, до 64 байт.
2. CAN к рейке: classic 50, 8 байт.
3. Таблица до 30 мест × 2 канала (значение, статус, возраст).
4. Приём с рейки → обновить слот по месту.
5. Раз в 1 с → пачка FD на ПЛК (3–4 кадра).
6. Приём с ПЛК: сборка AO → classic на модули; CFG / ID / FWUPD — мост на рейку.
7. Убрать как основной режим мгновенный форвард каждого `0x301` на ПЛК.
8. Таймаут слота → в сборке статус «нет связи».

Локомотив **не интерпретирует** смысл величин.

---

## 5. Прошивка ПЛК

1. Порт магистрали: FD 125 / 64 байт.
2. Разбор сборки локомотива → источники `(rail, place, channel)`.
3. Комнаты, уставки AO, мониторинг — только через конфиг.
4. Периодически: кадры комнат; сборка AO (по изменению + редкий refresh 1–2 с).
5. Хабы и реле на той же магистрали — тот же FD/скорость.
6. Веб/мониторинг: модуль/канал + роль из конфига, не только климат.
7. ID-walk и обновление прошивок — под FD на магистрали.

ПЛК — единственный, кто по конфигу решает смысл данных и задания на AO.

---

## 6. Прошивка хаба и дисплея

**Хаб:** сторона ПЛК — FD 125; сторона дисплеев — classic 50; мост комнаты/дверей/привязки дисплея; AI-сборки не трогает.

**Дисплей:** без FD; фильтр по комнате; показ из кадра комнаты.

---

## 7. Конфигуратор (приложение)

1. Каналы: AI/AO, тип величины, привязка к оборудованию/комнате.
2. Файл конфига на ПЛК: line/rail/place, каналы, signal, quantity/role, min/max.
3. Предупреждения: нет роли, дисплей без комнаты и т.п.
4. Мониторинг: рейка → модуль → канал → значение + расшифровка из схемы.
5. Для монтажа: BUS и RJ45 = одна магистраль; локальные CAN AI/дисплеев отдельно.

---

## 8. Логика обмена (сквозная)

```
Приложение (схема)
  → файл конфигурации на ПЛК
       ↓
AI/AO модуль  --classic 50-->  Локомотив  --FD 125 сборка-->  ПЛК
       ↑                              ↑                         ↓
   задание AO ←── classic ←── разборка ←── FD сборка заданий ←──┘
                                                         ↓
                                              кадр комнаты / команды
                                                         ↓
                                              Хаб --classic 50--> Дисплей
```

| Кто | Что | Как часто (ориентир) |
|-----|-----|----------------------|
| Каждый AI/AO (входы) | кадр 8 байт на рейку | 1 раз/с |
| Локомотив → ПЛК | сборка рейки FD | 1 раз/с (3–4 кадра) |
| ПЛК → хаб | кадр комнаты | 0,5–1 с |
| ПЛК → дисплей (через хаб) | привязка комнаты | ~1 с |
| AO вниз | пачка FD + classic на модуль | по изменению + refresh 1–2 с |
| CFG / ID / прошивка | по событию | не циклически |

Поочерёдный опрос модулей локомотивом **не** является основным ускорителем: узкое место — периоды и сборка на магистрали, не запрос-ответ.

## 9. Оценка нагрузки (ориентир)

Условие: 10 локомотивов × 30 аналоговых модулей, измерения 1 раз/с, сборка FD на магистрали.

- Магистраль вверх: ~10 × (3–4) ≈ **30–40 кадр/с** (не 300 и не 900).
- При 125 кбит FD — с большим запасом; запас можно нарастить скоростью data-phase.
- Обратный поток AO учитывать, но при пачках и «по изменению» не убивает бюджет.
- Рейка classic 30 модулей × 1 Гц — порядка единиц–десятков % на 50 кбит.
- Перевод рейки AI↔локомотив на FD: **выгоды мало**, минусы — перепрошивка всех вагонов и сложность; **не делать** без отдельной причины.

## 10. Порядок внедрения

1. Спека сборных кадров в `hvac_can` (+ этот документ).
2. Cube: FD только на связи ПЛК ↔ один локомотив; рейка AI без изменений.
3. Локомотив: буфер + сборка вверх; ПЛК: разбор (временно можно принимать и старый `0x301`).
4. Стенд: цифры в API и на дисплее.
5. Сборка AO вниз.
6. Хаб/реле на FD магистрали.
7. Убрать зеркальный форвард `0x301` с магистрали как основной режим.
8. Расширение типов величин в приложении; регрессия комнатных дисплеев.
9. Нагрузочный тест (эмуляция 30 слотов), период 1 с.

---

## 11. Риски

1. Не соединять локальный CAN AI/дисплеев с магистралью.
2. Терминаторы — только на физических концах всей магистрали.
3. Все головы на магистрали — один режим FD и одна скорость.
4. После перехода на элементы 64 байт — проверить Message RAM в Cube.
5. Не смешивать на магистрали старые classic-only узлы с FD без совместимого режима.
