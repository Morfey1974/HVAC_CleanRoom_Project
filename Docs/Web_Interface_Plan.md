# План веб-приложения HVAC CleanRoom

Документ — основа ТЗ на `Web_Interface/`. Собраны цели, принципы конфигуратора, единый стиль (взят из приложения **WEB order management**), правила таблиц и текста (включая иврит), модель данных и этапы работ.

## 1. Назначение и цели

Система имеет три интерфейса с общим стилем, языками и названиями:

| Интерфейс | Назначение | Где работает |
|-----------|------------|--------------|
| **Конфигуратор** | Только настройка системы и загрузка конфигурации в ПЛК (цели 9, 10, 11) | Веб-приложение на ПК инженера |
| **Монитор** | Отображение всей системы и живых значений, аварии, журнал, тренды, отчёты (цели 1–8, 12) | Веб-приложение на ПК/сервере, любое число рабочих мест |
| **HMI 10"** | Местная панель оператора у щита: комнаты, значения, аварии, уставки | Отдельная плата на STM32H723 + ёмкостный сенсорный дисплей 10" |

Цели ниже относятся к системе в целом; в какой интерфейс входит каждая — указано в таблице выше по номерам.

| № | Цель | Кратко |
|---|------|--------|
| 1 | Мониторинг помещений | Температура, влажность, перепад давления, класс чистоты по зонам в реальном времени |
| 2 | Мониторинг оборудования | Вентиляторы, частотники, клапаны/дамперы, нагрев, охлаждение, увлажнение, фильтры, двери: состояние, мощность, неисправности |
| 3 | Уставки | Нужные значения по зонам с допусками; права на изменение по ролям |
| 4 | Аварии | Выход за допуски, обрыв датчика, потеря связи с модулем, пожарная сигнализация, ИБП; квитирование с фиксацией пользователя и времени |
| 5 | Журнал | События, аварии, изменения уставок и конфигурации — с точным временем (RTC ПЛК) |
| 6 | Тренды и отчёты | Графики за часы/дни/месяцы; выгрузка для аудита чистых помещений (PDF / CSV) |
| 7 | Расписания | Дневной/ночной режим, выходные, энергосбережение |
| 8 | Диагностика сети | Карта шины CAN: ПЛК → локомотивы → вагоны, хаб дисплеев; связь, ошибки, версии прошивок |
| 9 | **Конфигурирование блоками** | Вся настройка — перетаскивание блоков-модулей на экран конфигуратора (раздел 4) |
| 10 | Обновление прошивок | Удалённо, через CAN-загрузчик |
| 11 | Доступ | Вход по паролю; роли: просмотр, оператор, инженер, администратор |
| 12 | Интеграция | Передача данных в SCADA по Modbus TCP |

Приоритет при конфликтах: **безопасность процесса и корректность данных > сохранность конфигурации > удобство > производительность**.

## 2. Размещение и этапы запуска

1. **Сейчас — локально.** Приложение работает на компьютере инженера (браузер + локальный сервер). Связь с ПЛК по Ethernet в локальной сети.
2. **Режим без железа (симулятор).** Конфигурацию можно собирать и проверять без подключённого ПЛК; значения датчиков — демонстрационные. Нужен для разработки и продаж.
3. **Позже — выгрузка на ресурс** (сервер / облако). Архитектура сразу закладывается так, чтобы переезд не требовал переделки: конфигурация, журнал и тренды хранятся на сервере приложения, ПЛК — источник живых данных и исполнитель.
4. Лёгкая страница на самом ПЛК (Flash + LwIP) — только аварийный доступ: состояние и сброс аварий. Полное приложение на ПЛК не размещается.

### Технологии (как в WEB order management — для единообразия)

| Часть | Выбор |
|-------|-------|
| Интерфейс | React + TypeScript + Vite, `react-router-dom` |
| Языки | `i18next` + `react-i18next`, файлы `ru.ts`, `en.ts`, `he.ts` |
| Сервер | .NET 9 (C#), схема **Controller → Service → AppDbContext → PostgreSQL** (без отдельного Repository) |
| Хранилище | PostgreSQL (конфигурации, версии, журнал, тренды), миграции EF Core |
| Запуск | `docker-compose` (как в образце) |
| Связь с ПЛК | Modbus TCP / собственный протокол поверх TCP (решить на этапе 1) |
| PDF | QuestPDF, шрифты `NotoSansHebrew` + `NotoSans` |

**Структура страниц — как в WebUI проекта Industrial Door PLC** (`Industrial Door PLC 8 Doors/WebUI`): заставка → вход → шапка (логотип, статус связи с ПЛК: сеть, линк, IP, ошибка связи, колокольчик аварий, язык, пользователь) + левое меню из трёх пунктов **Мониторинг / Конфигуратор / Настройки** → страницы в папках `pages/Monitoring`, `pages/Configuration` (вкладки), `pages/Settings`. Переносятся: `ProtectedRoute` (права по страницам), `LeaveConfirmContext` (предупреждение о несохранённых изменениях), `ErrorBoundary`, `StateDataContext` (опрос состояния ПЛК), редактор привязок `Mapping` — основа редактора мнемосхем. Отличия: TypeScript вместо JS, i18next с ru/en/he и RTL вместо одного `ru.json`, стиль — из WEB order management (раздел 5).

## 3. Языки: русский, английский, иврит

### 3.1 Общие правила (перенесены из образца)

- **Все строки интерфейса** — только через i18n (`ru.ts`, `en.ts`, `he.ts`). Текст прямо в разметке запрещён.
- **Выбор основного языка — в самом приложении**: переключатель в шапке + «язык по умолчанию» в настройках системы. Выбор пользователя запоминается.
- При смене языка выставляются `<html lang>` и `<html dir>`: **RTL для иврита, LTR для ru/en** (`applyDocumentDirection`, как в образце).
- В стилях — **только логические свойства**: `margin-inline-start`, `padding-inline-end`, `inset-inline-end`, `border-inline-start`, `text-align: start`. Никаких `left/right` — тогда при иврите интерфейс зеркалится сам.
- **Текст, введённый пользователем** (названия комнат, оборудования, примечания), может быть смешанным: иврит + латиница + цифры. Для него — компонент **`BidiText`** и класс **`.bidi-auto`** (`dir="auto"`, `unicode-bidi: plaintext; text-align: start`). Для полей ввода — `bidiAutoInput()`.
- PDF — шрифты `NotoSansHebrew` + `NotoSans`, корректный порядок смешанного текста (как `PdfReportFormat` в образце).

### 3.2 Дополнительные правила для HVAC

- **Технические значения всегда LTR**: диапазоны `0–10 V`, `4–20 mA`, `0–100 %`, IP-адреса, CAN-адреса, версии прошивок, номера клемм. Оборачиваются в отдельный класс `.ltr-value` (`direction: ltr; unicode-bidi: isolate`), чтобы в ивритском тексте не переворачивались.
- **Единицы измерения** хранятся отдельно от числа и переводятся (°C, %RH, Pa, м³/ч).
- **Названия** комнат и оборудования вводятся на каждом языке (`nameRu`, `nameEn`, `nameHe`) и **выводятся на выбранном языке приложения**: переключил язык — сменились и названия комнат/оборудования на всех экранах, в отчётах и журнале. Если перевод не заполнен — показывается название на языке объекта по умолчанию, а в конфигураторе поле подсвечивается как незаполненное.
- **Зеркалирование конфигуратора**: палитра блоков в RTL переезжает вправо, но **картинки модулей не зеркалятся** — клеммы и нумерация должны совпадать с реальным устройством.
- Графики трендов: ось времени всегда слева направо (стандарт), подписи осей — на выбранном языке.

## 4. Конфигуратор — главный принцип

Вся настройка системы — это **перетаскивание блоков-картинок** из палитры на рабочее поле и заполнение их параметров. Каждый блок уже описан внутри (какие у него каналы, сигналы, ограничения).

Общая раскладка экрана: **палитра блоков** (сбоку, в RTL — справа) | **рабочее поле** | **панель свойств выбранного блока**. У каждого блока в углу — шестерёнка ⚙ (открывает свойства) и индикатор состояния.

### 4.0 Проекты и общая библиотека (структура приложения)

Приложение начинается со страницы **«Проекты»**. Вся конфигурация (разделы 4.1–4.14) живёт внутри проекта.

**Верхний уровень (без открытого проекта):**

| Раздел | Содержание |
|--------|------------|
| Проекты | Карточки проектов, поиск; «Создать проект», «Копировать», «В архив» / «Восстановить». Пометка «На объекте» у активного проекта |
| Библиотека | Общая для всех проектов: модули, датчики и приборы, исполнительные устройства, типовые узлы, графика мнемосхем, регуляторы. У элемента: код, название (3 языка), производитель, модель, описание, характеристики (параметр / значение / ед.) |
| Система | Общие настройки (язык при запуске, источник данных), пользователи, журнал действий |

**Создание проекта — мастер:** 1) общие данные (название 3 языка, номер, заказчик, адрес, ответственный, класс ISO, описание); 2) P&ID (можно пропустить); 3) таблица AOI (можно пропустить); 4) «Создать». После создания открываются разделы проекта.

**Разделы проекта (левое меню, сверху «← Проекты» и название проекта):**

| Группа | Разделы |
|--------|---------|
| Проект | Обзор (данные, готовность по этапам, «Сделать активным на объекте»), Документы (P&ID, AOI, прочее) |
| Разбор | Разбор P&ID, Разбор AOI (4.8) |
| Конфигурация | Помещения, Оборудование (из библиотеки), Сигналы, Железо, Привязка, Регуляторы, Мнемосхемы |
| Работа | Мониторинг, Аварии, Пусконаладка |
| Записи | Журнал проекта, Выгрузка в ПЛК |

**Библиотека ↔ проект.** Проект берёт из библиотеки **копию элемента с номером версии**. Каждое сохранение элемента в библиотеке — новая версия. Проект сам не меняется: показывает «есть новая версия» и обновляется только по кнопке «Обновить», с записью в журнал (GMP).

**Активный проект.** С ПЛК объекта связан один проект — «на объекте». Мониторинг и аварии работают только для него; остальные проекты — для подготовки и редактирования.

### 4.1 Вкладка «Объект и помещения»

- Общие параметры объекта: название, адрес, часовой пояс, единицы, язык по умолчанию.
- Опционально — подложка плана этажа (картинка), поверх которой ставятся комнаты.
- Блок **«Комната»**: название (3 языка), класс чистоты ISO, площадь/объём, уставки и допуски (T, RH, ΔP), режимы день/ночь, связанное расписание.
- Быстрые действия: копировать комнату, шаблон «типовая чистая комната».

### 4.2 Вкладка «Оборудование»

Палитра: приточная установка (AHU), вентилятор с частотником, нагреватель (водяной/электрический), охладитель, увлажнитель, дампер/клапан, фильтр с датчиком перепада, дверь (шлюз), датчик в помещении, ИБП, пожарная сигнализация.

- Блок перетаскивается в комнату или внутрь AHU.
- Каждый тип оборудования заранее знает **свои сигналы-гнёзда**. Пример:
  - дампер: команда положения (AO), обратная связь положения (AI), концевики (DI);
  - вентилятор с частотником: пуск (DO или реле), скорость (AO 0–10 V / 4–20 mA), авария (DI), работа (DI);
  - электронагреватель ступенчатый: ступени (реле, по одному на ступень), защита от перегрева (DI), контроль контактора (DI);
  - нагреватель плавный: мощность (AO), защита от перегрева (DI);
  - любое ON/OFF оборудование (насос, увлажнитель, лампа, контактор): включение (реле или DO), обратная связь «работает» (DI).
- Для каждого выхода (AO, DO, реле) задаётся **безопасное состояние** при потере связи: выключить / удержать / заданное значение. Для нагревателей по умолчанию — выключить.
- Пустые гнёзда видны на блоке; пока не заполнены — блок жёлтый.
- Для частотников по RS-485: адрес Modbus, модель из библиотеки.

### 4.3 Вкладка «Железо» (сеть CAN)

Собирается «как поезд»:

- **Главный ПЛК** — всегда на поле, показывает шины FDCAN1–3, Ethernet, RS-485.
- **Локомотив** «сцепляется» с шиной ПЛК.
- **Вагоны** (AI, AO, DI, DO, реле) «сцепляются» с локомотивом.
- Каждый модуль на поле подписан: системное имя, артикул, серийный номер, место (раздел 8.3).
- **Хаб дисплеев** и **дисплеи** подключаются так же.
- Картинка модуля повторяет реальный: видны клеммы-каналы с номерами.

**Сделано (этап 1, таблица):** страница проекта «Модули ПЛК» — список по группам (ПЛК, рейки, вне цепочки ID); добавление модуля из библиотеки с выбором линии/рейки/места по его виду, подсказкой свободного места и живым просмотром ID, системного имени и каналов (AI-01.05/1…/2); ожидаемый серийный номер, ревизия, имя на 3 языках. Поле «как поезд» — следующий этап поверх этих же данных.

**Сделано (этап 2, «Схема системы»):** поле в стиле drawio. Слева палитра модулей библиотеки (перетащить на поле или двойной щелчок), в центре поле с масштабом, мини-картой и сеткой, справа выбранный модуль с его точками связи и куда они подключены, проверки и спецификация по артикулам.
- Провод тянется от точки связи; пока он тянется, подсвечиваются только подходящие свободные точки (тот же тип, не вход-вход и не выход-выход; питание 24 В можно разводить на несколько модулей).
- Модуль, брошенный на поле, стоит «без номера» (LOC-?, AI-?) и получает место по проводам: линия ПЛК → головной (эта линия + свободная рейка); выход головного на кабель → следующий головной (та же линия, новая рейка); выход локомотива на рейку → первый вагон (место 01); выход вагона → следующий вагон (+1); порт хаба N → дисплей (место N). Уже пронумерованные модули не сдвигаются. Порядок проведения проводов не важен.
- Провода редактируются: выбранный провод поднимается над модулями, показывает «+» на серединах отрезков (потянуть — появится излом) и квадратики изломов (тянуть — двигать, двойной щелчок — убрать); двойной щелчок по проводу добавляет излом в этом месте. Изломы прилипают к сетке и выравниваются по соседним точкам, чтобы легко получать прямые углы. У угловой линии отрезки двигаются целиком (полоска на середине); если отрезок совпал по уровню с соседним, лишние изломы исчезают и участки сливаются в одну прямую; двойной щелчок по угловой линии делает обход-«ступеньку». Вид линии: угловая, прямая, плавная; «Сбросить маршрут» возвращает автоматическую прокладку. Маршрут — это оформление (как положение блоков), в журнал не пишется.
- Удаление модулей и проводов — клавишей Delete через окно подтверждения с причиной; всё пишется в журнал (провод проведён/удалён, модуль получил номер по схеме, обновлён из библиотеки).
- Тип сигнала каналов: в библиотеке у модуля отмечаются допустимые типы (0–10 В, 2–10 В, 0–5 В, 0–20 мА, 4–20 мА, Pt100, Pt1000, NTC 10 кОм); в проекте для каждого канала выбирается ровно один — в окне модуля («Модули ПЛК») или в боковой панели схемы. Сервер не принимает тип, которого модуль не поддерживает; изменение пишется в журнал; значение уходит в прошивку модуля.
- Проверки: нет ПЛК; модуль без номера; не задан тип сигнала канала; вход головного не подключён; вагон или дисплей не подключён на схеме; в библиотеке есть новая версия модуля (кнопка «Обновить из библиотеки»; провода к исчезнувшим точкам удаляются).
- Таблица «Модули ПЛК» и схема — одни и те же данные; модули без номера в таблице показаны отдельной группой.

**Редактор блока модуля** (библиотека → модуль → вкладка «Блок и точки связи»): размер блока (угол тянется мышью), цвета фона, шапки, текста и рамки, готовые наборы цветов, заголовок, подпись, показ артикула; точки связи — добавить, копировать, удалить, перетащить мышью (у края прилипают к рамке), название, тип, направление, свой цвет, роль в нумерации (с номером линии ПЛК или порта хаба); свободные надписи с размером, жирностью и цветом; «разложить точки ровно», привязка к сетке, масштаб, отмена (Ctrl+Z), стрелки для точного сдвига. Рисунок хранится в элементе библиотеки и входит в его версию; проект держит свою копию. У стандартного ряда HC-… рисунок по умолчанию уже задан.

Свойства **канала** (по ⚙ на модуле → список каналов):

| Поле | Пример |
|------|--------|
| Тип сигнала | 0–10 V, 4–20 mA, 0–20 mA, PT100/PT1000, NTC, сухой контакт |
| Что измеряется | температура, влажность, давление, положение… |
| Шаблон датчика | «Датчик T/RH 0–10 V» — подставляет пределы автоматически |
| Пределы | 0–10 V → 0–100 %RH; 0–10 V → 0–50 °C |
| Единицы, точность | °C, 1 знак |
| Калибровка | смещение, коэффициент |
| Фильтр | сглаживание, с |
| Аварийные пороги | низкий/высокий, задержка |
| Реакция на обрыв | ниже 3.8 mA / выше 20.5 mA → авария «обрыв датчика» |

- **Библиотека датчиков**: готовые шаблоны + свои, сохранённые пользователем.
- **«Найти модули»** — опрос шины, найденные модули автоматически появляются на поле.
- **«Мигнуть»** — светодиод на выбранном модуле мигает, чтобы найти его в шкафу.
- Двухканальный датчик (T + RH) — один шаблон занимает два канала.

### 4.4 Вкладка «Привязка»

- Канал модуля тянется мышью к гнезду оборудования (линия связи), либо выбирается из списка — для тех, кому так быстрее.
- **Проверки на лету**: выход нельзя привязать к входу; тип сигнала должен совпадать; один канал — одно гнездо; незаполненные гнёзда подсвечены.
- Таблица привязок (в стиле `DataTablePanel`) — для проверки и печати.

### 4.5 Цвета состояния блоков

| Состояние | Цвет |
|-----------|------|
| Не настроено | серый (`--palette-gray`) |
| Настроено не полностью | жёлтый (`--warning`, новый токен) |
| Всё в порядке / есть связь | зелёный (`--success`) |
| Авария / нет связи | красный (`--error`) |

### 4.6 Черновик, проверка, загрузка

1. Работа идёт в **черновике** (можно без железа).
2. **«Проверить»** — список ошибок и предупреждений со ссылкой на блок.
3. **«Загрузить в систему»** — конфигурация уходит в ПЛК; ПЛК раздаёт по CAN каждому локомотиву/вагону его часть (тип сигнала, пределы, пороги). Модуль сам переводит V/mA в инженерные единицы и отправляет наверх готовые значения.
4. Каждая загрузка — **версия** с автором, временем и контрольной суммой; откат к прошлой версии; сравнение версий.
5. Экспорт/импорт конфигурации файлом (перенос на другой объект).
6. Защита от потери: предупреждение при уходе со страницы с несохранёнными изменениями (`UnsavedLeaveDialog`, как в образце).

### 4.7 Мастер первого запуска

«Загрузить P&ID и таблицу входов/выходов (4.8) → проверить черновик → объект → комнаты → оборудование → найти модули → привязать → проверить → загрузить». Без файлов заказчика — те же шаги вручную по шаблонам. Всё, что мастер создал, потом правится обычным конфигуратором.

### 4.8 Импорт P&ID и таблицы входов/выходов (с помощью ИИ)

Перед каждым проектом заказчик выдаёт **P&ID** (схема системы в AutoCAD) и **таблицу входов/выходов** (Excel: теги, типы сигналов, диапазоны датчиков). Конфигуратор строит из них черновик проекта; инженер только проверяет и правит.

**Таблица входов/выходов (Excel/CSV)** — основной и точный источник:
1. Загрузка файла → ИИ сопоставляет колонки заказчика с нашими полями (тег, описание, комната, тип сигнала, диапазон, единицы, пороги аварий). Сопоставление показывается таблицей, инженер подтверждает; шаблон сопоставления запоминается для следующих проектов этого заказчика.
2. Каждая строка → канал: тип сигнала (AI/AO/DI/DO/реле), шаблон датчика, пределы (0–10 V → 0–50 °C), пороги.
3. Конфигуратор сам считает, **сколько каких модулей нужно**, раскладывает каналы по рейкам и выдаёт **спецификацию по артикулам** (`HC-AI2` × 3, `HC-RL4` × 2 …) для склада и заказа.

**P&ID (DWG/DXF/PDF)** — источник структуры:
1. DWG конвертируется в DXF (ODA File Converter) или загружается PDF.
2. Из DXF читаются текстовые теги и блоки (TT-101, HT-101, PDT-102, FAN-01, DMP-03); для PDF — распознавание изображения ИИ (модель с «зрением»).
3. ИИ по тегам и подписям определяет комнаты, оборудование, датчики и связи «датчик → комната / оборудование», сверяет с таблицей входов/выходов.
4. Результат — черновик во вкладках 4.1–4.4. Каждый распознанный элемент имеет пометку уверенности: зелёный — совпало с таблицей, жёлтый — предположение ИИ, красный — не удалось определить. Ничего не загружается в ПЛК без подтверждения инженера.

Технически: ИИ вызывается с сервера приложения (ключ API хранится на сервере, не в браузере); работает и без ИИ — ручное сопоставление колонок и ручная расстановка.

**Решение: облачный ИИ.** Настройка и загрузка в ПЛК делаются на компьютере инженера (с интернетом); ПЛК дальше работает автономно, ИИ ему не нужен.

Как читается P&ID (порядок обработки):
1. **DWG/DXF — точные данные без ИИ.** В чертеже AutoCAD каждый символ — это блок с именем (например, «ISA_TT») и атрибутами (TAG = TT-101, описание). Программа читает блоки, атрибуты, тексты, слои и линии напрямую (библиотека ezdxf). Покупать «все обозначения» не нужно: их форма нам не важна, важны имя блока и атрибуты. Для каждого заказчика один раз составляется таблица «имя блока → наш тип» (ИИ предлагает, инженер подтверждает, таблица запоминается).
2. Если P&ID сделан в AutoCAD Plant 3D / AutoCAD P&ID — в нём уже есть база тегов; её можно выгрузить в Excel средствами AutoCAD и загрузить как таблицу.
3. **Облачный ИИ с «зрением»** — только для того, что не читается напрямую: PDF/скан, нестандартные блоки без атрибутов, связи «датчик → комната/оборудование».
4. Результат — **граф P&ID** в нашем формате (JSON, совместимый по смыслу с DEXPI): элементы, теги, комнаты, связи. В приложении чертёж показывается интерактивно (DXF → SVG в браузере): щелчок по символу → карточка элемента, цвет — статус привязки. На основе графа строится управление (4.1–4.4, 4.13).

Готовые платные сервисы (Pathnovo, Novek AI, PNID.IO) выдают теги и связи из P&ID в Excel/JSON/DEXPI, но рассчитаны на крупные EPC-проекты и дороги; держим как запасной вариант. Dify (конструктор ИИ-процессов) можно использовать для быстрого прототипа обработки; в итоговой версии та же цепочка встраивается в сервер Конфигуратора, чтобы не зависеть от стороннего сервиса.

Сравнение облачного и локального ИИ (для справки):

| | Облачный | Локальный |
|---|---|---|
| Качество на сложных P&ID | Высокое | Ниже, больше жёлтых/красных пометок |
| Интернет | Нужен | Не нужен |
| Данные заказчика | Уходят в облако | Остаются на компьютере |
| Место на диске | — | 5–20 ГБ (модель с «зрением») |
| Железо | Любое | Видеокарта 8–16 ГБ, иначе медленно (минуты на лист) |
| Стоимость | Оплата за запрос (копейки–рубли за проект) | Бесплатно после установки |
| Обучение | Не нужно | Не нужно |

Обучать модель не нужно: она получает инструкцию и 2–3 разобранных примера. Точные данные (теги из DXF, строки таблицы) читает сама программа без ИИ; ИИ только сопоставляет и связывает. Сервер приложения делается с переключаемым поставщиком ИИ (облако / локальная модель).

### 4.9 Двери (Doors PLC)

- От Doors PLC по CAN3 приходит только **состояние каждой двери: открыта / закрыта**.
- В свойствах дампера (и вентилятора, при необходимости) — реакция на открытие связанной двери, задаётся для каждого проекта:
  - **ничего не делать**;
  - **остановить** сразу;
  - **ждать N секунд**, затем остановить, если дверь всё ещё открыта.
- Возврат в работу — после закрытия двери (с настраиваемой задержкой).

### 4.10 Дисплеи 4.3" у хаба

- Только отображение, уставки менять нельзя.
- Показывают данные одной комнаты: температура, влажность, давление (авария — красное мигание параметра).
- В Конфигураторе: порт хаба → комната. Используется существующая прошивка отображения дисплея.

### 4.11 Аварии и уведомления

- Сбившийся параметр **мигает красным** на HMI, дисплеях 4.3" и в Мониторе; неисправный датчик (обрыв, выход за диапазон, нет связи с модулем) — тоже красным, со своим текстом причины.
- В шапке Монитора и HMI — **красный колокольчик без звука** с числом активных аварий. Нажатие → журнал активных аварий; оттуда — вкладка истории (все аварии за период, фильтры, выгрузка).
- Каждая авария пишется в журнал аварий: начало, значение, квитирование (кто, когда), устранение. При устранении запись переходит в историю.
- Звук — не используется.
- Почта — заложено, пока заглушка.
- СМС — позже, через существующее GSM-оборудование для шкафов управления.
- Аварийный релейный выход — позже, по необходимости (канал релейного модуля с ролью «общая авария»).

### 4.12 RS485 для внешних ПЛК

- Протокол Modbus RTU (ПЛК — ведомый) реализуется, но пока **заглушка**: отвечает на запросы, таблица регистров пустая/тестовая.

### 4.13 Регуляторы

- Первые типы: **ПИД температуры**, **ПИД влажности**, **ПИД давления** (в комнате). Каскад давлений — не сейчас.
- Регулятор — отдельный объект библиотеки (`RegulatorType`): входы (датчики), выходы (оборудование), параметры, режимы. Новые типы добавляются в библиотеку без переделки Конфигуратора, ПЛК исполняет их по номеру типа.
- В Конфигураторе — вкладка «Регуляторы»: комната → регулятор → датчик → исполнительное оборудование → уставка и пределы.

### 4.14 Пусконаладка (проверка входов/выходов)

- Режим пусконаладки включает инженер; все выходы переводятся в **ручное управление**, автоматика и регуляторы не работают. На экране — постоянная жёлтая плашка «Пусконаладка».
- Основа — **таблица AOI** проекта: каждая строка — канал. Для выходов — кнопки вкл/выкл или задание значения (AO), для входов — живое значение.
- Колонка **«Проверено»** (галочка), кто и когда проверил, примечание.
- **Печать протокола проверки входов/выходов** (PDF): проект, дата, инженер, таблица с отметками.
- Все ручные действия пишутся в журнал. Выход из режима — возврат выходов в безопасное состояние, затем автоматика.

### 4.15 Поведение при пропадании и возврате питания — ⚠ ТРЕБУЕТ СОВМЕСТНОЙ ПРОРАБОТКИ

Решения пока не приняты. Обсудить отдельно и вместе: автозапуск после восстановления питания или ожидание оператора; порядок включения оборудования (вентиляторы → дамперы → нагрев/увлажнение); задержки между ступенями; что делать, если питание пропало во время пусконаладки или обновления прошивки.

### 5.4 Правила таблиц (из `DataTablePanel` образца)

- **Одна панель**: заголовок со счётчиком («Модули · 12»), фильтры, таблица, пагинация — единый блок.
- Панель **меняет размер** за три полоски в нижнем углу; ширина растёт симметрично от центра, высота — вниз; размер запоминается.
- **Колонки**: ширина меняется перетаскиванием границы заголовка и запоминается; значения по центру, **текстовые колонки (названия) — по началу строки** (`.dt-col-text-start`).
- **Заголовки**: мелкий шрифт, заглавные буквы, приглушённый цвет, лёгкий бирюзовый фон; сортировка по клику с индикатором.
- **Строки** — отдельные скруглённые блоки с зазором, без вертикальных линий; **подсветка при наведении**.
- Пагинация: 25 / 50 / 100 / 200 строк, выбор сверху и снизу.
- Действия в строке: круглая «+» и меню «⋮» в последней колонке.
- Поля фильтров скруглены (8px).
- Пустая таблица — понятное сообщение по центру.

### 5.5 Картинки модулей и оборудования

- Формат SVG, единая стилистика (контур, фирменные цвета), одинаковый масштаб.
- Клеммы на картинке — активные точки (для привязки и подсказок).
- Набор: ПЛК, локомотив, AI, AO, DI, DO, релейный модуль, хаб дисплеев, дисплей 4.3" / 10.1", AHU, вентилятор, частотник, нагреватель, охладитель, увлажнитель, дампер, фильтр, дверь, датчики.
- **Мнемосхема AHU** (решение 2026-10-07: сначала плоский вид со склейкой секций, см. 5.7) — изометрический (объёмный) вид в духе обучающих иллюстраций: корпус из секций (смешение/клапаны, префильтр, HEPA, нагрев, охлаждение, увлажнитель, вентилятор с двигателем и частотником, приточный воздуховод). Каждая секция — отдельный SVG-блок; установка собирается автоматически из секций по P&ID и конфигурации.
- Живое поведение: стрелки потока воздуха движутся при работе вентилятора; нагрев краснеет, охлаждение синеет пропорционально выходу; клапаны поворачиваются по положению; рядом с секцией — значения (T, RH, ΔP фильтра, % частотника); авария — секция мигает красным; щелчок — карточка оборудования.
- Готовые растровые картинки (в т.ч. сгенерированные ИИ) — только как фон/иллюстрации; всё, что показывает значения, — вектор. Для HMI 10" те же блоки выгружаются в картинки для TouchGFX.

### 5.6 Живая и конструируемая графика (принцип для всех экранов)

**Правило: вся графика живая и собирается из готовых элементов, без программирования.** Касается мнемосхем AHU, планов помещений, схемы железа (рейки, модули, кабели), экранов HMI и дисплеев.

**Графический элемент** (`GraphicElement`) — единица библиотеки:
- рисунок SVG с именованными частями (лопасть, заслонка, спираль нагрева, стрелка потока, лампа, поле значения);
- **точки подключения** (вход/выход воздуха, воды, сигнала) — элементы «прилипают» друг к другу;
- **привязки**: какие данные влияют на какую часть и как.

Типы оживления (набор фиксированный, комбинируется в любом элементе):

| Оживление | Пример |
|-----------|--------|
| Цвет по значению / состоянию | Нагрев: серый → красный по % выхода; авария — мигание красным |
| Поворот | Заслонка по % открытия, стрелка прибора |
| Вращение / движение | Лопасти вентилятора, бегущие стрелки потока (скорость — по частотнику) |
| Заполнение | Уровень, % загрязнения фильтра |
| Показ / скрытие | Значок «ручной режим», «нет связи», «пусконаладка» |
| Текст значения | T, RH, P, %, с единицами и языком приложения |
| Щелчок | Карточка оборудования, уставка (по правам роли) |

**Как собирается графика:**
1. **Автоматически** — из P&ID и конфигурации: установка собирается из секций, комната — из её датчиков и оборудования, рейка — из найденных модулей.
2. **Редактор мнемосхем** в Конфигураторе — перетаскивание элементов из палитры, соединение точек подключения, привязка к данным выбором из списка (не вводом адресов), сетка и выравнивание, копирование секций и целых установок, шаблоны («AHU приток-вытяжка», «чистая комната с тамбуром»).
3. **Предпросмотр с симулятором** — ползунками меняются значения, видно, как оживает схема, до загрузки в ПЛК.

**Добавление новых элементов:** новый элемент = SVG + описание частей и привязок (файл JSON) — добавляется в библиотеку через Конфигуратор, без переделки приложения. Элементы имеют версии; схемы проектов ссылаются на версию.

**Одна схема — везде:** Монитор, веб-Монитор ПЛК, HMI 10" (элементы переводятся в картинки и анимации TouchGFX при формировании пакета HMI), облако. Направление справа налево (иврит) — зеркалится раскладка текста, а не технологическая схема.

### 5.7 Редактор HMI и ИИ-помощник — решения от 2026-10-07

Обсуждено на документах проекта NanoMotion 26000017 (P&ID, AC-1 Unit layout 4056, архитектура, электрика P3017-01). Эти решения уточняют 5.5–5.6 и 4.8.

**Вид.** Пока **плоский** вид (не изометрия). Секции установки — одной высоты, разной длины; новая секция встаёт вплотную к предыдущей, порядок меняется перетаскиванием; корпус, верх и низ рисуются одной линией по всей установке — стыков не видно. Масштаб условный: важен порядок секций. Позже — второй ряд (приток над вытяжкой, рекуператор). Изометрия под постоянным углом — возможное развитие, не сейчас.

**Уточнение 2026-10-07 (вечер): общий стиль всей системы.** По образцу разрезного рисунка установки и фото реальных установок на объекте: установка показывается **под углом** (косоугольная проекция, глубина уходит вверх-вправо), корпус **прозрачный** (светло-серые стёкла-панели с контуром дверей и ручками, рама-основание снизу), внутри подробно нарисованы агрегаты: фильтры в зелёных рамках со складками и загрязнением, теплообменник с ламелями и медными трубками и вентилем, ТЭНы с подсветкой ступеней и клеммной коробкой в жёлто-чёрную полосу, синий корпус вентилятора с крыльчаткой и оранжевым мотором, широкие стрелки воздуха (холодный — голубой, приток — оранжевый), снаружи — козырёк забора и оцинкованный воздуховод «Supply Air». Фон **светлый**, яркие цвета; тёмный фон не используем. Склейка секций и перетаскивание сохраняются. Этот стиль — основа для остальных картинок системы (оборудование, комнаты).

**Комнаты** — плитки **в ряд**: название, класс ISO, температура, влажность, перепад давления, двери; рамка меняет цвет при отклонении. Точная карта по плану не обязательна.

**3D** всего объекта — отдельный режим просмотра (большой монитор, руководство), не для работы оператора. Позже.

**Библиотека HMI** — отдельный раздел приложения, **не** библиотека модулей. Общая для всех проектов:
- элемент: вид оборудования (общий словарь: вход воздуха, фильтр, охладитель, нагреватель, вентилятор, увлажнитель, заслонка, выход, наружный блок VRF, FFU, кондиционер, плитка комнаты, дверь, датчик), название на 3 языках, рисунок со всеми состояниями (стоит / работает / авария), длина, места для значений, версия, статус **черновик / утверждён**; другим проектам видны утверждённые;

- нового элемента нет → создаётся черновик прямо из проекта, рисуется, утверждается и становится общим.
- Первое наполнение — по NanoMotion: вход свежего воздуха, фильтры 12 % / 30 % / 95 %, охладитель от VRF, электронагреватель 3 ступени, вентилятор EC, выход в воздуховод, наружный блок VRF, FFU, кондиционер, плитка комнаты; черновики — увлажнитель (изменение 02 P&ID), заслонка.

**Экраны HMI в проекте** (раздел «Мнемосхемы»): установка из секций, ряд плиток комнат; привязка каждого места значения к сигналу проекта выбором из списка; проверка на симуляторе, затем на ПЛК; показ в «Мониторинге».

**ИИ-помощник — облачный.** Основной поставщик — Google Gemini (ключ Google AI Studio, бесплатный уровень; подписка Antigravity сама ключ не даёт), запасной — ключ Cursor (Cursor SDK). Подписка ChatGPT к приложению не подключается. В настройках — переключатель поставщика и поле ключа (хранится только на сервере приложения). Документы заказчика разрешено отправлять в облако (заказчик — DCM). От проектировщиков дополнительно запрашиваются DWG/DXF.

**Связь редактора и помощника** — общий словарь видов оборудования. Помощник называет найденное этими видами, редактор по ним берёт элементы библиотеки.

**Этапы:**

## 8. Связь с железом

- В `Shared_Libs/` создать **`can_protocol.h`** — общее описание сообщений CAN (живые значения, настройка каналов, статус, загрузчик). Приложение, ПЛК, локомотивы и вагоны используют одинаковые номера и структуры.
- Передача конфигурации: приложение → ПЛК (Ethernet) → локомотив → вагон (CAN), с подтверждением и контрольной суммой; модуль хранит свою часть в энергонезависимой памяти.
- Масштабирование (V/mA → единицы) выполняет модуль; ПЛК и приложение получают готовые значения. Сырые значения доступны в диагностике.
- Время событий — от RTC ПЛК; часы ПЛК синхронизируются с компьютером сервера приложения (при каждом подключении и раз в сутки), HMI берёт время у ПЛК.
- При потере связи с приложением ПЛК продолжает регулирование по последней загруженной конфигурации.

### 8.0 Карта связи: кто с кем и по какому каналу

| Кто ↔ кто | Канал | Что передаётся |
|-----------|-------|----------------|
| Браузер Конфигуратора / Монитора ↔ сервер приложения | Локальная сеть (HTTP + WebSocket для живых значений) | Экраны, конфигурация, живые значения, отчёты |
| Сервер приложения ↔ ПЛК | Ethernet, TCP (свой протокол), поиск по UDP; **одно** соединение от сервера | Конфигурация, прошивки (от Конфигуратора); подписка на живые значения и аварии (для Монитора); время |
| HMI 10" ↔ ПЛК | Ethernet, тот же протокол, отдельное соединение (через DIN-коммутатор) | Пакет HMI (экраны, названия на 3 языках), живые значения, аварии, уставки |
| Сервисный ноутбук ↔ ПЛК | USB Type-C (вирт. COM) | Первичная настройка IP, диагностика, аварийная прошивка |
| ПЛК ↔ локомотивы на других DIN-рейках | CAN1 / CAN2 ПЛК (развязанные) — кабель | Настройки, значения, прошивки; ПЛК пересылает данные между локомотивами разных реек |
| Локомотив ↔ свои модули на рейке | CAN1 локомотива — шина рейки + линия адресации MODUL_ID | Настройки каналов, значения датчиков, прошивки (локомотив — ретранслятор) |
| Локомотив ↔ ПЛК или другие локомотивы | CAN2 локомотива — кабель (напрямую к ПЛК или через ПЛК) | Готовые значения рейки, команды, конфигурация, прошивки |
| ПЛК ↔ Doors PLC + модули расширения | CAN3 (развязанный, модуль питания+CAN) + линия адресации MODUL_ID_OUT_BUS = **линия 3 (BUS)** | Состояния дверей (Doors PLC — постоянный адрес); модули на этой линии — идентификация цепочкой, как на линиях 1–2 |
| Внешние контроллеры предприятия → ПЛК | RS485, Modbus RTU, **ПЛК — ведомый** (только отвечает на запросы) | Чтение значений и состояний; запись — только разрешённых регистров |
| ПЛК ↔ часы FRTC8900S | I2C1 (разъём платы часов) | Точное время при пропадании питания |
| ПЛК ↔ память настроек AT24C256 | I2C2 | Сетевые настройки, серийный номер, последняя конфигурация |
| ПЛК ↔ флеш W25Q128 | QSPI | Образы прошивок, резерв конфигурации, журнал, аварийная веб-страница |
| Отладка ПЛК | USART3 (разъём) + SWD | Журнал отладки, программатор |

Правила:
- Модули нижнего уровня никогда не общаются с приложением напрямую — только через ПЛК.
- Каждая CAN-линия независима: обрыв одной не останавливает остальные.
- Адрес модуля в поезде определяется по линии MODUL_ID (цепочкой: каждый модуль после получения адреса «передаёт эстафету» следующему) — настраивать адреса вручную не нужно.
- Периодичность: живые значения — 1 раз в 0,5–1 с или по изменению; аварии — сразу; «я жив» от каждого модуля — 1 раз в секунду (пропал 3 раза подряд → авария «нет связи»).

### 8.0.1 Вывод в Монитор

- ПЛК — источник данных. Сервер приложения держит **одно** соединение с ПЛК и подписывается на изменения (значения — по изменению или 1 раз в 0,5–1 с, аварии — сразу).
- Сервер пишет тренды, аварии и журнал в PostgreSQL и рассылает живые значения во все открытые Мониторы через WebSocket (SignalR). Число рабочих мест не нагружает ПЛК.
- Названия комнат/оборудования Монитор берёт из той же конфигурации, что создал Конфигуратор, — на выбранном языке.
- Команды оператора из Монитора (квитирование, уставки) идут через сервер в ПЛК с проверкой роли и записью в журнал.
- Если сервер выключен — Монитор недоступен, но ПЛК и HMI продолжают работать; аварии за это время ПЛК хранит во флеш и отдаёт серверу после восстановления связи.

### 8.0.2 Вывод на HMI 10"

- Плата HMI (STM32H723, LTDC + внешняя SDRAM/флеш для графики, ёмкостный сенсор по I2C) подключается к ПЛК по **Ethernet** через DIN-коммутатор (ПЛК, HMI, сервер). CAN для HMI не используется — у него мало скорости, а шины заняты модулями.
- При загрузке конфигурации Конфигуратор формирует **пакет HMI**: список комнат и экранов, названия на 3 языках, привязки значений, картинки. Путь: Конфигуратор → ПЛК → HMI; HMI хранит пакет в своей флеш.
- В работе HMI подписывается у ПЛК на живые значения и аварии тем же протоколом, что сервер; от сервера не зависит.
- Уставки и квитирование с HMI — по PIN-коду роли; ПЛК проверяет пределы и пишет в журнал.
- Язык HMI выбирается на панели; иврит — справа налево (графическая библиотека с поддержкой RTL, например TouchGFX).
- Прошивка HMI обновляется так же, как ПЛК: Конфигуратор → ПЛК → HMI по Ethernet.

### 8.1 Канал приложение ↔ ПЛК — Ethernet

- Физика: RJ45 на ПЛК (LAN8742A, 100 Мбит/с), сервер приложения в той же локальной сети; позже — через VPN/шлюз для доступа из интернета.
- Протокол: TCP-сервер в ПЛК (LwIP), собственный протокол «запрос/ответ + подписка на изменения»; для сторонних SCADA дополнительно Modbus TCP (только чтение/уставки).
- Поиск ПЛК: широковещательный UDP-запрос «кто здесь» → ПЛК отвечает серийным номером, IP, версией.
- Безопасность: пароль/токен сессии, отдельный порт сервиса, запись всех команд в журнал ПЛК.
- USB (Type-C, виртуальный COM-порт) — сервисный канал для первичной настройки IP и аварийного восстановления.

**Решение по сети (принято):**
- ПЛК управляет всеми устройствами сам; сеть нужна только для конфигурации, HMI и просмотра. Пропадание сети не влияет на работу объекта.
- ПЛК, HMI и компьютер-сервер подключены к **заводской локальной сети**. ПЛК — **постоянный IP** (задаётся в Конфигураторе, первично и при потере — через USB).
- Доступ **из любой точки заводской сети**: пользователь открывает Монитор/Конфигуратор в браузере с любого компьютера → сервер приложения → ПЛК. Вход по логину и паролю, права по роли.
- ПЛК принимает соединения **только от сервера и HMI** (список разрешённых адресов + ключ соединения); к ПЛК напрямую из сети никто не заходит. Канал сервер ↔ ПЛК шифруется (TLS).
- Сторонние SCADA — через Modbus TCP только на чтение (и уставки по разрешению), включается в настройках, по умолчанию выключен.
- Доступ снаружи завода — только через заводской VPN, средствами IT предприятия.

**Веб-сервер в ПЛК (STM32H723):**
- Лёгкий веб-Монитор в ПЛК **возможен**: страницы (сжатые, ~1–2 МБ) лежат во флеш, живые значения — через WebSocket, журнал и тренды — с флеш/microSD. Одновременно 2–4 браузера. Вход по логину, роли.
- **Не помещается** в ПЛК: Конфигуратор (редактор, импорт P&ID с ИИ, библиотеки), большие отчёты, много пользователей сразу. Это остаётся на компьютере.
- Итог: для просмотра из заводской сети компьютер-сервер не обязателен — браузер открывает адрес ПЛК. Сервер на компьютере — для Конфигуратора и длинной истории.

**Облако (будущее, этап 7):**
- ПЛК сам подключается **наружу** к облачному серверу (как телефон к мессенджеру), шифрованно, и отправляет туда значения и аварии. Открывать входящие порты в сети завода не нужно.
- Пользователь с любого места заходит в облачный Монитор по логину. Команды (уставки) идут из облака в ПЛК по тому же соединению, только разрешённые и с журналом.
- Пропал интернет — ПЛК работает дальше и досылает данные после связи.

### 8.2 Обновление прошивок всех модулей

1. Инженер загружает в приложение пакет прошивки (файл с типом модуля, версией, контрольной суммой и цифровой подписью).
2. Приложение по Ethernet передаёт образ в ПЛК блоками с подтверждением; ПЛК сохраняет его во внешнюю флеш-память (W25Q128, 16 МБ — хватает на образы всех типов модулей и предыдущие версии для отката).
3. ПЛК проверяет контрольную сумму и подпись целого образа до начала рассылки.
4. Рассылка по CAN: ПЛК → локомотивы → вагоны/дисплеи. Локомотив работает как ретранслятор: пересылает блоки своим вагонам, сам образ целиком не хранит.
5. Модуль по команде «перейти в загрузчик» перезапускается в загрузчик, стирает область программы, принимает блоки (номер блока + данные + контрольная сумма), подтверждает каждый пакет блоков.
6. Одинаковым модулям (например, всем модулям AI) образ рассылается **одновременно** (групповая рассылка), затем каждый сообщает список недостающих блоков — досылаются только они.
7. После приёма модуль проверяет контрольную сумму всей программы; только при совпадении помечает её рабочей и запускает. Иначе остаётся в загрузчике и ждёт повторной загрузки — модуль не «окирпичивается».
8. Собственная прошивка ПЛК: образ во внешней флеш → перезапуск → загрузчик ПЛК копирует во внутреннюю память → проверка → запуск; при ошибке — откат на предыдущий образ из флеш. Аварийно — через USB (заводской загрузчик STM32, перемычка BOOT0).
9. Порядок: сначала вагоны, затем локомотивы, затем ПЛК; перед обновлением — проверка совместимости версий протокола.
10. Экран «Прошивки» показывает прогресс по каждому модулю, итог и запись в журнал.

Ориентир по времени: CAN 50 кбит/с → образ 64 КБ ≈ 30–45 с на группу одинаковых модулей.

### 8.3 Идентификация модулей: артикул, серийный номер, ID, имя

У каждого модуля **четыре разных признака**. Их нельзя смешивать:

| Признак | Что означает | Одинаков у… | Кто задаёт | Где хранится | Пример |
|---------|--------------|-------------|------------|--------------|--------|
| **Артикул** | Что это за изделие (для склада, заказа, прайса) | всех одинаковых модулей | производитель | этикетка, память модуля (код типа), каталог | `HC-AI2` |
| **Серийный номер** | Какой именно это экземпляр | ни у кого (уникален) | производство, один раз | этикетка + QR, OTP-область МК (записывается один раз) | `2641-0017` |
| **ID (место)** | Где модуль стоит в системе | всех модулей на этом месте после замены | ПЛК при идентификации | ОЗУ модуля (заново при каждом включении), конфигурация | `1.03.05` |
| **Имя** | Как модуль называет человек | — | системное — автоматически, пользовательское — инженер | конфигурация | `AI-03.05` / «Щит 3, входы комнаты 101» |

Главный принцип: **конфигурация привязана к месту (ID), а не к серийному номеру.** Поэтому при замене сломанного модуля на такой же (тот же артикул) на то же место ничего перенастраивать не нужно — ПЛК сам загрузит в новый модуль настройки места.

#### 8.3.1 Артикул (номенклатура склада)

Формат: **`HC-<ТИП><КАНАЛЫ>[-<ИСПОЛНЕНИЕ>]`**, только латиница и цифры (одинаково на всех языках, читается слева направо). `HC` — префикс линейки (HVAC CleanRoom, можно заменить торговой маркой). Производитель всех модулей — **DCM Doors Control Making**.

| Артикул | Изделие | Код типа (в памяти модуля) |
|---------|---------|----------------------------|
| `HC-PLC` | Главный ПЛК (STM32H723) | 0x01 |
| `HC-DPLC` | Doors PLC | 0x02 |
| `HC-LOC` | Локомотив (головной модуль рейки) | 0x10 |
| `HC-AI2` | 2 аналоговых входа (0–10 V / 4–20 mA / PT) | 0x20 |
| `HC-AO2` | 2 аналоговых выхода (0–10 V / 4–20 mA) | 0x30 |
| `HC-DI8` | 8 дискретных входов 24 V | 0x40 |
| `HC-DO8` | 8 транзисторных выходов 24 V | 0x50 |
| `HC-RL4` | 4 реле (силовые ON/OFF цепи) | 0x60 |
| `HC-HUBD9` | Хаб дисплеев на 9 портов | 0x70 |
| `HC-TFT43` | Дисплей 4.3" (подключается к порту хаба) | 0x71 |
| `HC-HMI10` | Панель HMI 10" | 0x80 |
| `HC-PWRCAN` | Вставной модуль питания + развязанный CAN | 0x90 |
| `HC-CAN2` | Вставной модуль двух развязанных CAN | 0x91 |

Вставные модули (0x9_) — только комплектующие для сборки основных модулей: в продуктовую линейку и библиотеку приложения не входят.

- Цифра в артикуле = число каналов (числа — пример, уточнить по платам). Другое число каналов = другой артикул (`HC-AI4`, `HC-RL8`).
- Исполнение — только если меняется назначение/подключение: `HC-RL4-16A` (реле 16 А), `HC-AI2-PT` (только термосопротивления).
- **Ревизия платы** (A, B, C…) в артикул не входит: совместимые ревизии взаимозаменяемы и хранятся на складе под одним артикулом. Ревизия пишется на этикетке и хранится в памяти модуля — по ней выбирается подходящая прошивка.
- Код типа старшим полубайтом задаёт семейство (0x2_ — AI, 0x6_ — реле…), младшим — вариант. По коду ПЛК понимает, какой модуль ответил, и Конфигуратор показывает нужную картинку.

#### 8.3.2 Серийный номер

- Формат **`ГГНН-XXXX`**: год и неделя выпуска + порядковый номер за неделю (`2641-0017` — 2026 г., 41-я неделя, 17-й модуль). Сквозной для всех артикулов — два модуля с одинаковым номером невозможны.
- Записывается на производстве вместе с кодом типа и ревизией в OTP-область микроконтроллера (стереть и перезаписать нельзя, прошивка его не трогает). Дополнительно модуль сообщает заводской 96-битный UID микроконтроллера — защита от ошибок записи.
- Используется для: учёта на складе и гарантии, журнала замен, отслеживания прошивок.

#### 8.3.3 ID модуля = его место в системе

Запись **`Л.РР.ММ`**:

| Часть | Значение | Диапазон |
|-------|----------|----------|
| `Л` | Линия ПЛК: 1 = AI (CAN1, MODUL_ID_OUT_AI), 2 = DISPLAY (CAN2, MODUL_ID_OUT_DISPLAY), 3 = BUS (CAN3, MODUL_ID_OUT_BUS) | 1–3 |
| `РР` | Номер рейки (локомотива) — сквозной по объекту | 01–30 |
| `ММ` | Место модуля на рейке, считая от локомотива | 00 — сам локомотив, 01–31 — вагоны |

- ПЛК — `0.00.00`. Doors PLC на CAN3 имеет постоянный зарезервированный адрес (не выдаётся модулям) и в идентификации не участвует: на запрос «кто здесь» не отвечает. Если у Doors PLC нет выхода ID, он подключается к CAN3 вне цепочки ID (или последним), а модули расширения на линии 3 нумеруются цепочкой от выхода MODUL_ID_OUT_BUS ПЛК.
- Номер рейки сквозной, поэтому для пользователя достаточно «Рейка 3, место 5» (`03.05`); линия показывается в диагностике.
- В CAN: на шине рейки (CAN1 локомотива) адрес = `ММ`; на кабеле (CAN2 локомотива ↔ ПЛК) адрес = `РР`. Локомотив подставляет номер рейки при пересылке. Идентификатор кадра = тип сообщения + адрес (раскладка — в `can_protocol.h`).

#### 8.3.4 Процедура идентификации (по линиям оптронов MODUL_ID)

У каждого модуля есть **вход ID** (оптрон) и **выход ID**. Два вида опроса:

- **Цепочка** (рейка с вагонами, кабельная линия локомотивов): модуль получил ID → поднимает свой выход → отвечает следующий.
- **Звезда** (хаб дисплеев): у хаба 9 отдельных опросных выходов, по одному на порт. Хаб поднимает выход порта N → отвечает дисплей этого порта → его место = N. Дисплеи опрашиваются по очереди, пустой порт = нет ответа.

Хаб дисплеев на кабельной линии ведёт себя как локомотив: вход/выход ID и CAN2 — на кабель (к ПЛК и дальше), CAN1 — своя шина дисплеев. Дисплей на порту 3 хаба, стоящего рейкой 04, имеет ID `1.04.03`, системное имя `TFT-04.03`.

1. При включении все модули без ID молчат и слушают шину. Отвечать на запрос «кто здесь» модуль имеет право **только если его вход ID поднят и ID ещё не присвоен** — поэтому в каждый момент отвечает ровно один модуль, столкновений нет.
2. ПЛК поднимает выход ID линии 1 → отвечает первый локомотив (код типа, серийный номер, ревизия, версии прошивки и загрузчика).
3. ПЛК присваивает ему рейку `01`, локомотив подтверждает и по команде поднимает свой выход «на кабель» → отвечает следующий локомотив → рейка `02` и т.д. Нет ответа за 200 мс — конец линии. Затем то же для линии 2 (нумерация реек продолжается).
4. Каждый локомотив так же нумерует свою рейку: поднимает выход «на рейку» → первый вагон → место `01` → вагон поднимает свой выход → место `02`… Хаб дисплеев вместо цепочки опрашивает свои 9 портов по очереди. Готовый список локомотив/хаб отдаёт в ПЛК.
5. После обхода все выходы ID опускаются. Вся процедура — 1–3 с. Выполняется при каждом включении и по кнопке «Найти модули».
6. Если модуль поднял выход ID, а следующий по конфигурации модуль не ответил — это место обрыва: ПЛК выдаёт «цепочка прервана после 03.04».

Сверка найденного с загруженной конфигурацией:

| Ситуация на месте | Реакция |
|-------------------|---------|
| Тот же артикул, тот же серийный | Норма |
| Тот же артикул, другой серийный | Замена модуля: настройки загружаются автоматически, запись в журнал «замена 2641-0017 → 2702-0003», уведомление в Мониторе |
| Другой артикул | Ошибка «на месте 03.05 ожидался HC-AI2, найден HC-DO8»; модуль остаётся заблокированным |
| Модуль не найден | Авария «нет модуля 03.05» |
| Лишний модуль | «Найден новый модуль» — предлагается добавить в Конфигураторе |

Безопасность: выходные модули (AO, DO, реле) после включения держат выходы в безопасном состоянии, пока не получат ID **и** конфигурацию; при потере связи дольше заданного времени — переходят в безопасное состояние (раздел 4.2).

#### 8.3.5 Имена

- **Системное имя** — автоматически, неизменяемое, латиницей: `<тип>-<РР>.<ММ>`: `LOC-03`, `AI-03.05`, `RL-03.06`. Канал: `AI-03.05/2`. Одинаково на всех языках, используется в журнале, привязках, выгрузках.
- **Имя пользователя** — на трёх языках, по желанию: «Щит 3 — входы комнаты 101». Показывается на выбранном языке приложения рядом с системным.
- «Мигнуть» по системному имени — светодиод на модуле мигает, чтобы найти его в шкафу.

#### 8.3.6 Этикетка модуля

Артикул и название изделия, ревизия платы, серийный номер, QR-код (артикул + серийный), пустое поле для надписи места при монтаже (`03.05`).

## 9. Роли и безопасность

| Роль | Права |
|------|-------|
| Просмотр | Только смотреть |
| Оператор | Квитировать аварии, менять уставки в пределах, разрешённых инженером |
| Инженер | Конфигуратор, калибровка, расписания, загрузка конфигурации |
| Администратор | Пользователи, прошивки, резервные копии, настройки системы |

- Пароли — только в виде хэша; секреты не хранить в git (как в образце).
- Все изменения — в журнал.
- Требования чистых помещений (GMP): роли и права настраиваются (набор прав на каждое действие, роли выше — шаблоны); вход по личному логину; автоматический выход при бездействии; журнал нельзя редактировать или удалять; изменение уставок и конфигурации — с указанием причины.
- **Журнал действий**: кто, когда, откуда (компьютер/HMI), что изменил, старое/новое значение, причина.
- **Статистика**: входы пользователей, действия по пользователям, аварии по комнатам и оборудованию (число, длительность), наработка оборудования, изменения уставок; фильтры по периоду, выгрузка PDF/CSV.

**Где хранится:**

Система должна вести журнал **без компьютера** (только ПЛК + HMI на двери шкафа), поэтому основное хранилище — в ПЛК.

| Место | Что | Объём / срок |
|-------|-----|--------------|
| Флеш ПЛК W25Q128 (16 МБ) | Прошивки для обновления (~4 МБ), конфигурация, веб-страницы (~2 МБ); **журнал действий и аварий** (~8 МБ) | ~250 тыс. записей по 32 байта — годы при обычной работе; по кругу |
| **microSD в ПЛК (добавить на плату, SDMMC2)** | Тренды, статистика, архив журнала | Карта 8–32 ГБ промышленная: тренды 200 точек раз в 10 с ≈ 2,5 ГБ/год — на годы |
| Сервер приложения (если есть компьютер) | Копия всего из ПЛК, отчёты | Сколько угодно |
| HMI | Ничего не хранит, читает из ПЛК | — |

- Без microSD тренды в ПЛК помещаются только на ~2 недели (200 точек раз в минуту).
- Запись на microSD — пачками раз в минуту (карта живёт дольше); журнал аварий дублируется во флеш.

- Резервная копия базы сервера — автоматически раз в сутки на другой диск/сетевую папку; срок хранения трендов задаётся в настройках (по умолчанию — год, если хватает места).

## 11. Решения и открытые вопросы

### 11.1 Принято

1. Протокол приложение ↔ ПЛК — собственный поверх TCP; Modbus TCP — для сторонних SCADA (8.1).
2. Главная копия конфигурации — в ПЛК; на сервере приложения — резервная и версии.
3. Регуляторы: ПИД температуры, влажности, давления; библиотека расширяемая (4.13).
4. Роли, права, журнал, статистика по требованиям GMP; хранение — сервер + буфер во флеш ПЛК (9).
5. Тренды и журнал — хранить год (настраивается), если хватает места.
6. Телефон/планшет — пока не нужен.
7. Язык при запуске — выбирается в Настройках.
8. Аварии — красное мигание, колокольчик без звука, журнал активных и история (4.11).
9. Пусконаладка — ручное управление по таблице AOI, галочки «Проверено», печать протокола (4.14).
10. Сеть — заводская ЛВС, постоянный IP ПЛК, доступ через сервер из любой точки завода (8.1).
11. Время ПЛК — синхронизация с компьютером сервера.
12. Программа производства не нужна; этикетки модулей — подготовить позже.
13. Doors PLC (4.9), дисплеи 4.3" (4.10), RS485 — заглушка (4.12).
14. ИИ для P&ID — облачный; DWG/DXF читается напрямую, ИИ — для остального (4.8).
15. Журнал и аварии хранятся в ПЛК (система работает без компьютера); лёгкий веб-Монитор в ПЛК; облако — ПЛК подключается наружу (8.1, 9).
16. Приложение начинается со страницы «Проекты»; мастер создания проекта с загрузкой P&ID и AOI; общая библиотека с версиями, проект хранит копии элементов; один проект активен на объекте (4.0).
17. Нумерация 8.3 встроена в приложение: модули библиотеки — только по артикулу HC-… с кодом типа и префиксом имени (стандартный ряд 8.3.1 заводится автоматически); в проекте модуль ставится на место Л.РР.ММ, приложение само считает ID и системное имя и проверяет правила 8.3.3 (один ПЛК, головной на месте 00, вагоны 01–31 за локомотивом, дисплеи на портах хаба 1–9, вставные не размещаются, серийный ГГНН-XXXX уникален). Все подтверждения действий — собственные окна приложения в едином стиле, с полем причины для журнала; окна браузера не используются.
18. «Схема системы» — поле в стиле drawio с проводами между точками связи; подсветка только совместимых точек; ID модулей назначаются автоматически по проводам (роли точек: линия ПЛК, вход головного, выход на кабель, выход на рейку, вход/выход вагона, порт хаба, вход дисплея). Вид каждого модуля (блок, цвета, тексты, точки связи и их роли) полностью настраивается в библиотеке визуальным редактором и версионируется вместе с модулем (4.3).
19. Тип сигнала каналов задаётся однозначно и отдельно для каждого канала (например, AI2: канал 1 — 0–10 В, канал 2 — 4–20 мА). Библиотека перечисляет допустимые типы модуля (у HC-AI2 и HC-AO2 — 0–10 В и 4–20 мА), в проекте каждому каналу выбирается ровно один; незаданный канал — замечание на схеме. Настройка уходит в прошивку модуля при выгрузке в ПЛК (4.3).
